# アーキテクチャ方針

## 目的

- ブラウザで使える Web 版と、スマホネイティブ版（iOS / Android）を提供する。
- 両者で業務ロジックと型を共有し、機能追加を一度の実装で両方に届ける。

## 技術選定

### Web: Next.js

店長・オーナーがシフト表を作成する画面は、PC の大きな画面で表を扱う操作が中心になります。
SEO が効く紹介ページも同じアプリで持てるため、Web は Next.js を採用しました。

### モバイル: Expo（React Native）

アルバイトスタッフはスマホでシフト確認・希望提出・通知受信を行います。
Expo を使うと、Web と同じ React / TypeScript の知識でネイティブアプリを作れ、
EAS Build / Submit でストア配信、EAS Update で審査を待たない修正配信ができます。

> Expo 単体で Web も出力できますが、PC 向けの管理画面の作りやすさと Web の配信性能を重視して、
> Web は Next.js、モバイルは Expo と役割を分けています。

### 共通パッケージ: `@shifton/core`

- Zod スキーマでドメインモデル（店舗・メンバー・シフト・希望シフト）を定義し、型と入力検証を共有する。
- 日またぎ勤務を含む実働時間計算、シフトの重複検出、メンバー別集計などの純粋関数を置く。
- UI に依存しないため、Vitest で高速にテストできる。

今後、API クライアントや画面部品の共有が必要になったら `packages/` に追加します（例: `packages/api`）。

### バックエンド: Supabase

- PostgreSQL・認証・リアルタイム購読・ストレージを一つのサービスで揃えられる。
- 行レベルセキュリティ（RLS）で「同じ店舗のメンバーのみ閲覧」「店長のみ編集」といった権限をDB側で保証できる。
- Web・モバイルの両方から同じ SDK で接続できる。

スキーマは `supabase/migrations/` にあります。セットアップ手順は [supabase-setup.md](supabase-setup.md) を参照してください。

### 共通データアクセス: `@shifton/api`

Supabase クライアントを引数に受け取る関数（店舗一覧の取得、店舗作成など）を置き、Web とモバイルで共有します。
Web はサーバー側（Server Action / Server Component）で Cookie のセッションを使い、モバイルは端末内に保存したセッションを使います。

店舗作成は、店舗と「作成者をオーナーとするメンバー」を同時に登録する必要があるため、DB 関数 `create_store` でまとめて行います。

## 主要な機能ロードマップ（案）

1. ~~認証と店舗作成~~（実装済み）、スタッフ招待
2. 希望シフトの提出（スタッフ・スマホ）
3. シフト表の作成と公開（店長・Web）
4. 公開・変更時のプッシュ通知
5. シフト交代の申請と承認
6. 人件費・勤務時間の集計、給与計算向けの出力
