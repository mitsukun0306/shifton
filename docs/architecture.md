# アーキテクチャ方針

## 目的

- アルバイトをしている本人が、バイト先（外部）から届くシフトを取り込み、自分の予定として管理できるようにする。
- 掛け持ちでも、勤務先をまたいだ重なりの検出や、勤務時間・給与の目安をひと目で分かるようにする。
- ブラウザで使える Web 版と、スマホネイティブ版（iOS / Android）を提供し、業務ロジックと型を共有する。

店舗の管理者がシフトを作るためのアプリではありません。データはすべて「ログインしている本人のもの」です。

## 技術選定

### Web: Next.js

PC でまとめてシフトを確認・整理したり、ファイルを取り込んだりする用途に向けて、Web は Next.js を採用しました。
紹介ページも同じアプリで持てます。

### モバイル: Expo（React Native）

シフトの確認や、シフト表の写真・スクショの取り込みはスマホでの利用が中心になります。
Expo を使うと、Web と同じ React / TypeScript の知識でネイティブアプリを作れ、
EAS Build / Submit でストア配信、EAS Update で審査を待たない修正配信ができます。

### 共通パッケージ: `@shifton/core`

- Zod スキーマでドメインモデル（勤務先・シフト）を定義し、型と入力検証を共有する。
- 日またぎ勤務を含む実働時間計算、シフトの重なり検出、勤務先ごとの集計、日付の扱いなどの純粋関数を置く。
- UI に依存しないため、Vitest で高速にテストできる。

### 共通データアクセス: `@shifton/api`

Supabase クライアントを引数に受け取る関数（勤務先・シフトの取得、登録、削除）と入力検証を置き、Web とモバイルで共有します。
Web はサーバー側（Server Action / Server Component）で Cookie のセッションを使い、モバイルは端末内に保存したセッションを使います。

### バックエンド: Supabase

- PostgreSQL・認証・ストレージ（取り込む画像やファイルの保管）を一つのサービスで揃えられる。
- 行レベルセキュリティ（RLS）で「自分のデータしか読み書きできない」ことを DB 側で保証する。
- Web・モバイルの両方から同じ SDK で接続できる。

スキーマは `supabase/migrations/` にあります。セットアップ手順は [supabase-setup.md](supabase-setup.md) を参照してください。

## シフトの取り込み（これから実装）

バイト先によってシフトの配り方が違うため、複数の取り込み方法を順に用意します。
どの方法でも「読み取り → 自分のシフトだけ抽出 → 確認画面で修正 → 登録」という同じ流れにし、
登録したシフトには取り込み元（`shifts.source`: manual / image / file / import）を記録します。

1. **写真・スクショ**: 紙のシフト表の写真や、LINE・シフト管理サービスの画面のスクショを AI（画像認識）で読み取る。
   API キーを安全に扱うため、読み取りはサーバー側（Supabase Edge Functions または Next.js のサーバー）で行う。
2. **PDF・Excel**: バイト先から届くファイルを読み取り、自分の名前の行を抽出する。
3. **外部サービス連携**: シフト管理サービスやカレンダーとの連携。サービスごとに対応可否を調べる。
4. **書き出し**: Google カレンダーなど、普段使っているカレンダーへの反映。
